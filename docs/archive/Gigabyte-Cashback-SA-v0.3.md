## 2. 前言：原先猜想與需求訪談後的落差

### 2.1 原先的規劃假設

v0.2 在舊站資料尚未完整取得時，先將專案理解為「自營 Cashback 申請與審核網站」。當時假設以單一歐洲國家、單一品類、每件 Claim 一項產品試行，第一版就串接產品驗證 API 與 OCR，建立登入／會員中心，並以第三方付款 API 或 CSV 作業完成發放。

這些假設適合用來討論原型，卻尚未確認舊服務的全部責任、實際活動規則及公司會員系統的交付時程。現有 site 原型也是示意流程，不能據此認定功能、介接或業務規則已完成或已獲核准。

### 2.2 與需求單位溝通後確認的背景

需求單位，也就是業務單位，過去委託 Agency 建置活動網站，Agency 的服務還包含 Cashback 代付款及相關作業。業務主要提供設計畫面與需求架構，其餘由 Agency 承接。因為活動每次重做、每次收費，才希望改由內部單位建立可重複使用的平台。

因此，本次要承接的是「活動平台加上原服務中的必要作業」，不只是申請表單。審核、補件客服、付款、資金準備、對帳與異常處理，都必須重新分工；**由 IT 開發網站，不等於 IT 自動承接原 Agency 的全部營運責任。**

需求單位希望直接串接 AORUS Member 單一登入，取得會員資料，最好也取得註冊資料。活動設定、審核／稽核、後台與報表是基本需求。原 Agency 無法只承接目前設想的代付款方式，因此需另外評估供應商；Tremendous 為候選，尚未選定。

## 3. 來源、可信範圍與既有規則

### 3.1 來源使用方式

本次資料共 **110 份：1 份系統需求 PDF、1 份 FAQ DOCX、108 張 PNG**。其中包含兩季共 90 張市場 Landing Page、17 張其他前台頁面及 1 張後台總覽。所有檔案均列於來源清冊。

分析時區分：

- **本次需求**：本次訪談說明、三階段策略，以及 PDF 的需求描述；需納入討論。
- **舊站證據**：畫面、各季條款與 FAQ，證明舊站呈現或說明過哪些能力，不等於下一次活動全部沿用。
- **分析建議**：本文件提出的優先級、過渡方案、資料模型及安全控制，仍待核定。
- **未取得資訊**：SSO/API 契約、正式產品與通路矩陣、完整後台、付款作業 SOP、供應商合約等，不自行補成既定事實。

來源衝突必須由業務及相關負責單位確認；不能單靠新草案覆蓋舊活動對既有參加者的承諾。

## 4. 分期策略與正式上線條件

### 4.1 建置分期

| 階段 | 目標 | 必要交付 | 限制／完成條件 |
|---|---|---|---|
| Phase 1 | 可操作的 Cashback 核心流程 | 活動設定、申請、多產品、身分／會員資格處理、人工審核／補件、預算、通知、權限、付款紀錄與對帳、基本報表 | 可先用模擬服務做內部 UAT；正式收件須通過 4.2 |
| Phase 2 | AORUS Member 與產品資料整合 | SSO、授權會員資料、本人已註冊產品、SN／型號與 RMA／DOA 驗證整合 | 依實際 API 能力驗收；查不到／逾時有人工例外路徑 |
| Phase 3 | 付款與營運自動化 | 經選型的供應商 API、事件處理、對帳自動化、提醒與作業優化 | 不代表 Phase 1 可沒有付款承接方；必要時將最小付款整合提前 |

**商業必要性與實作方式分開判斷：** 會員資格、實際付款、可追蹤結果是業務 Must-have；SSO、產品 API、付款 API 是希望採用的整合方式。若業務要求首日就必須 SSO，則它是首日上線門檻，不能以本分期自行降級。

### 4.2 Phase 1 正式收件的五個門檻

1. **規則核定**：首波市場、金額、產品／通路矩陣、期間、預算、限制、條款及隱私告知均已核定。
2. **會員資格有依據**：取得可信的 AORUS 資格驗證方式。可討論受授權的查詢或人工核對，但 Email OTP 只證明信箱控制權，不能證明是 AORUS 會員。
3. **有人承接營運**：審核、客服、補件、退換貨、財務核放、資金準備、對帳與事故處理均有負責人、權限與 SOP。
4. **付款真的能執行**：公司財務或新供應商同意承接，確認國家、幣別、方式、資金、費用、時效、失敗補救及結果回傳；完成受控驗證。僅完成 CSV 匯出不算通過。
5. **安全及服務可維運**：存取控制、敏感檔案、通知、稽核、備份復原、支援聯絡方式與必要法務／資安核可完成。

未達門檻時，Phase 1 的交付應標示為 **內部 UAT／流程驗證版**，不得對外收取帶有 Cashback 承諾的真實申請。若唯一可用的付款途徑就是供應商 API，最小付款整合必須提前，而不是維持 Phase 3 排程後仍宣稱 Phase 1 已可營運。

### 4.3 首波活動選項

| 選項 | 內容 | 建議 |
|---|---|---|
| A：Q1 類型 | 選定市場、顯卡／主機板／螢幕、多明細、各品類固定回饋、同發票 | **建議基準**；降低組合規則複雜度但保留主要流程 |
| B：Q4 類型 | A 的完整流程，加 A／B 區資格與加碼重算、CPU 等額外品類證明 | 首波行銷需要組合加碼時採用；組合功能不得延期 |
| C：全面涵蓋兩季 | 廣泛市場、多語／RTL、多幣別及兩套活動規則 | 範圍最大；翻譯、付款覆蓋與客服量都要估算 |

選項 A 不稱為「完整還原 Q4」。任何進一步縮減品類、國家或功能，均要記錄為核定差異。

## 6. 核心業務流程與規則

### 6.1 申請及審核

建立／複製活動草稿 → 核對規則與預算 → 授權發布 → 使用者選市場與語言 → 確認身分及會員資格 → 填寫同發票的產品明細與購買證明 → 驗證期間／重複／限制 → 原子化占用名額及預算 → 取得 Claim Reference → 人工審核／補件／異常 Hold → 核准或拒絕 → 付款核放 → 對帳與通知。

案件受理、核准及付款是不同里程碑。會員／SN 查核中可以保留待審案件，但不得顯示為資格已通過；來源查核不可用時的收件與占額政策須核定，不能默認放行。

### 6.2 身分、會員與註冊產品

- AORUS 主系統管理註冊及密碼；Cashback 不收集 AORUS 密碼。SSO 的協定、Client 設定、登出、授權欄位及測試帳號待 API 單位確認。
- 過渡方案可評估信箱驗證搭配獲授權的會員資格查核，保存查核來源、時間及結果。完整會員清單匯入不是預設方案。
- 採內部 Applicant ID，後續連結不可變的 AORUS Subject／Member ID；不得只憑同名或相同未驗證 Email 自動合併身分。
- 已註冊產品用來減少輸入與協助檢核，不等於活動合格購買證明；仍需購買期間、通路、SN、發票等條件。
- 「僅可申請已註冊產品」目前未確認；不應因產品清單 API 不含某項產品就直接拒絕。
- Claim Reference 不是存取憑證；公開查詢至多顯示受限制的一般進度，個資、附件、補件、付款資料必須驗證本人。P1 可直接以驗證後查詢取代公開查詢。

### 6.3 申請單位與金額

- 一筆 Claim 對應一個活動版本、一位申請者、一張發票／同次交易、多個 ClaimItem。舊活動每品類最多一項，實際上限可設定。
- 同一發票可有多張影像／檔案，但不等於多張發票或多次購買。發票號碼不完整時，採日期、通路、金額與附件交叉查核，不能僅靠檔名去重。
- 每人／每戶上限與 SN 重複檢查獨立處理。地址可協助戶別核對，但同住不同人、地址格式差異需人工申訴，不靠地址文字直接做不可逆拒絕。
- Cashback 金額取自核定市場矩陣；活動幣別、居住國、購買國與銀行國並非同一件事。DACH 等市場群組不能只有一個固定幣別欄位。
- Q4 加碼必須驗證 A／B 關係與同次購買；A 項不合格時要重算 B 區資格，不能各項獨立相加。
- **建議 P1 不做分次／部分付款**：可逐明細檢核，待所有問題解決後，以一次最終核定額付款。若允許移除不合格品項，需保留原始申請、重算、理由及通知；是否允許此作法由 D06 核定，不能靜默減額。

### 6.4 期間、通路及文件

- 活動須分別設定購買期間、申請期間、購買後等待天數、補件期限、審核 SLA 與付款 SLA。過了購買日仍可能可以申請；停止新申請後仍需查詢、補件及付款服務。
- 時間以 UTC 保存，搭配明確活動時區與可讀的截止時間；確認 14 天按曆日差或 14 × 24 小時計算、邊界是否含當日，以及工作日曆／補件停表規則。
- 通路採有效清單搜尋與選取，不接受未匹配的自由文字直接視為合格。跨境可選其他允許購買國的通路，不能只依銀行國家過濾；跨境可用範圍仍依核定活動條款。
- 必須能取得發票上的通路、日期、產品及實付金額。是否另設輸入欄位／人工擷取由表單設計確認；不將 OCR 當成必需。
- 舊 FAQ 接受 JPG／TIF／PDF、每檔 8 MB；新站格式與大小需確認。可提議 JPG／PNG／PDF，若刪除 TIF 須明確核定，不宣稱相容性已還原。
- 保留必要姓名、聯絡、居住／戶別及收款資料。稱謂、電話、地址是否必填依用途決定；保留每戶限制時，不能同時無替代地刪掉戶別判定資料。
- 條款／隱私告知與選填行銷同意分開，保存適用版本與同意紀錄；不勾行銷不得阻擋申請。

### 6.5 RMA／DOA、補件、取消與更正

- P1 支援人工或受控批次查核後回填案件：檢核項目、來源、結果、查核時間、操作者及文件；P2 再接 API。單獨留在外部試算表而案件無紀錄，不算完成。
- 異常 Hold 阻止核准及新付款指令；解除須授權與理由。核准後、實際發出付款前再次檢查 Hold。
- API 逾時／查無資料是待查證，不是確定不合格；已發出付款後發現異常進例外處理，不假設一定能撤回。
- 瑕疵同型號換貨、換成不同型號、一般退貨分開記錄；依核定條款判斷新 SN、重新申請、取消或人工追償。保留舊／新 SN 關聯，不以換號洗掉重複查核。
- 補件不直接覆蓋歷史資料；重新查核受影響的金額、SN、資格及預算。付款資料變更不得直接改已送出的指令。
- 使用者提出取消後，須先確認是否已有對外付款指令／結果不明；無付款風險才能取消並釋放額度。已付或不明案件轉人工處理。

## 7. 審核、付款與預算模型

### 7.1 狀態分離

| 層次 | 建議狀態／資料 | 原則 |
|---|---|---|
| Claim Review | Submitted、UnderReview、MoreInfoRequired、Approved、Rejected、Cancelled | 補件回覆後回到待複核；不直接自動 Approved |
| Risk Hold | 無／待查證／異常待複核；原因、來源、解除紀錄 | 與審核狀態分開，核准後也可阻擋後續付款 |
| Payment Instruction | Ready、Authorized、Submitted、Processing、Unknown、Succeeded、Failed、Cancelled | 手動批次交付付款人後也須記錄 Submitted；單純產檔不是完成付款；Unknown 不自動重付 |
| Provider／Recipient | 供應商原始狀態、配送狀態、領取狀態、支付證據 | 寄達、開啟連結、領取獎勵與銀行入帳分別保存 |
| Case Timeline | 提交、驗證、補件、核准、預計付款、付款執行、對帳及通知時間 | Due Date 與 Actual Payment Date 不混用 |

Succeeded 的證據須按付款方式定義，例如付款承接方可對帳的完成紀錄；若只有「已安排」或「獎勵已寄出」證據，顯示相符文字，不能宣稱銀行已入帳。已核准仍可能付款失敗，兩者不可用同一狀態覆蓋。

### 7.2 預算與名額

每個核定預算池以同一幣別計算，金額採最小貨幣單位或精確十進位，不用浮點數。建議至少分開：

| 符號 | 定義 |
|---|---|
| B | 核定總 Cashback 預算 |
| F | 保留 Buffer |
| R | 尚未核准但已受理占額的案件 |
| A | 已核准、尚未確認完成支付的金額，含處理中／失敗／結果不明 |
| P | 已確認支付且仍計入活動成本的金額 |
| 可受理額度 | B − F − R − A − P |

R、A、P 為互斥餘額，不把「累計核准額」再與已付相加。核准將 R 移至 A；確認付款將 A 移至 P；退回待審需有對應反向異動。另呈現累計流量時須清楚標籤。

- 同時提交的資格限制、SN 占用、件數與金額占額須有交易一致性，避免超額或重複受理。
- 草稿不占額。補件中的案件是否占額、多久逾期釋放，由政策明訂；建議補件期限內保留，到期經處理再釋放。
- 付款失敗／不明不釋放已承諾的預算；取消、減額、退回或追償的異動都需有憑據。已付不能只改成 Rejected 就恢復預算。
- 總預算是主控制，件數為輔；達限自動停收且前台明示。門檻告警、調額、重開、Buffer 調整均留紀錄。
- 公開頁至少顯示可申請／接近額滿／已停收；是否公開精確剩餘金額另核定，避免把內部財務資料默認公開。
- 不同幣別不可直接相加。若採跨市場共用預算，需核定基準幣別、匯率及換算時點；否則先使用分幣別預算池。
- Cashback 預算、供應商儲值餘額、手續費／匯差為不同帳目，不因供應商有餘額就允許活動超支。

### 7.3 付款控制與人工路徑

付款最小閉環：核准案件 → 財務／授權角色核放 → 形成不可變付款指令 → 交付實際付款人 → 取得結果 → 逐筆核對金額／幣別／對象／憑證 → 回寫正確狀態與通知。

- 同一邏輯發放使用固定的 Payment Instruction ID／冪等鍵；技術重試只新增 Attempt，不產生新的邏輯款項。
- 金額／對象變更先停止或核清舊指令，再授權新版本；不能用新鍵繞過不明結果。
- 人工 CSV 同樣要有批次 ID、逐筆指令 ID、版本、總額、檔案雜湊、操作者與交付／回覆紀錄。重新下載同批次不是建立新付款；付款方須能識別重複指令。
- 批次可部分成功，對帳到明細；未匹配、金額不符、錯誤幣別及重複結果進例外清單。未確認是否付款的項目不得再次批量送出。
- P1 可採受控人工結果登錄，不預設供應商已支援特定 CSV 格式或回傳 API。是否需完整銀行欄位、哪些角色可見，取決於已選支付流程。

供應商選型必須取得的答案：

1. 國家 × 幣別 × 實際收款方式 × 金額範圍矩陣；能否保證銀行轉帳／指定現金方式，而非只能提供禮券。
2. 收款人是否要額外註冊、身份／合規檢查，誰收集銀行資料，失敗或逾期由誰支援。
3. 費率、匯率、預存／退回資金、未領取、過期、取消、對帳及稅務責任的合約安排。
4. 什麼證據可對應「已發出、已領取、已支付」，取得方式、頻率、識別碼與保存期限。
5. 個資處理、傳輸／保存地區、DPA、正式服務條件與客服責任；由公司相關單位審查。

若採供應商託管收款頁，可減少本系統持有銀行資料，但會改變舊表單、通知及使用者領款步驟，須先獲業務同意。Email／LINK 等配送模式也要確認；領款連結視為敏感憑證，不寫入一般日誌或公開頁面。

| BudgetLedger | 暫占／核准／支付／釋放／調整的不可混淆異動與幣別 |
| PaymentInstruction／Attempt／Batch | 邏輯付款、重試、外部 ID、核放、批次及資金核對；與 Claim 分開 |
| ProviderEvent／Reconciliation | 原始事件、安全驗證、去重、結果證據、對帳差異與處理人 |
| Notification／Consent／Audit | 發送／重寄紀錄、告知／同意版本、角色及操作事件 |

P1 外部依賴至少包含通知服務、受保護檔案儲存、會員資格核對與實際付款人。P2／P3 的介面可先以 mock 測試，但假資料需明示，UAT 環境禁用正式收款／付款憑證。

會員 API、產品／SN API 與 RMA／DOA API 不假設是同一服務或同一天完成。需要分別確認欄位、權限、查詢識別、資料新鮮度、限流、錯誤、服務窗口與測試樣本。

## 10. 營運分工及安全要求

### 10.1 責任建議，待各單位指派

| 工作 | 建議承接者 | 必須確認的內容 |
|---|---|---|
| 活動規則／預算／內容／市場 | 業務活動 Owner | 決策人、核定矩陣、翻譯與發布權 |
| 審核／補件／客訴／退換貨 | 業務指定營運或另委託團隊 | 人力、語言、工作日曆、處理量與 SLA |
| 核放／資金／對帳／付款異常 | 財務＋實際付款方 | 權限、費用、付款日、憑證、重付與追償 SOP |
| 平台／資安／備援／監控 | IT 開發與維運 | 服務窗口、故障處理、存取、復原目標 |
| AORUS／產品／售後資料 | 各資料與 API 維護單位 | 介面、授權、查核責任與交付時程 |
| 法務／隱私／內控 | 公司對應負責單位 | 條款、資料處理角色、保存、權利請求與供應商審查 |
| 供應商收款服務 | 經選定的供應商 | 僅依合約承接，不預設包括網站、資格審核或全部客服 |

角色至少區分活動管理、審核、客服、財務核放／對帳、系統管理與稽核檢視。可由同一人兼任的項目須經核准；操作權與能看哪些國家／活動資料分開控管。付款人不應僅因是系統管理員就自動有撥款權。

### 10.2 上線必需的工程與作業保護

- 後台強驗證／MFA 或公司既有受控登入；最小權限，限制批次下載與未遮罩銀行資料。
- 個資、附件與領款連結不公開；檔案類型／大小驗證、惡意檔案檢查或隔離，敏感資料傳輸與儲存保護。
- 操作紀錄涵蓋發布規則、預算、更正、核准、解除 Hold、付款、匯出與敏感存取；一般管理介面不可刪改稽核紀錄。
- 依資料種類訂保存與刪除政策；保留合法必要的財務／稽核證據。個資權利請求由授權作業處理，不讓刪除按鈕破壞未結案件對帳。
- 通知失敗、付款 Unknown、資金不足、額度接近上限及查核服務失效有告警與處理清單。
- 重試與背景工作具冪等；備份、還原演練、RPO／RTO、流量與附件容量目標在上線前核定。
- 響應式與鍵盤／錯誤提示等基本可及性；首波瀏覽器、語言及 RTL 依實際市場驗收。特定法規／標準由公司適用性審查，不在本稿宣稱已符合。

## 11. 報表及營運口徑

P1 提供可篩選的畫面及受控匯出；不要求先建資料倉儲或進階圖表。

| 報表 | 最低內容 |
|---|---|
| 案件與審核 | Submitted、待審、補件、核准、拒絕、取消、Hold；明確區分案件數與產品件數 |
| 產品／通路／市場 | 申請／核准明細、品類、SN、通路、購買國、活動市場與幣別 |
| 預算 | B／F／R／A／P／可受理額度、名額、門檻與調整歷程 |
| 付款與對帳 | 應付、核放、已送出、處理中、不明、失敗、已確認支付；批次、外部 ID、幣別及憑證 |
| 客服與 SLA | 待補件、到期、待處理查詢、審核／付款到期、通知失敗及異常負責人 |

報表需標示時間基準（提交日／核准日／付款日）、時區、資料更新時間與篩選條件。多幣別保留原幣；產品明細不能造成 Claim 件數重複加總。匯出個資與銀行資料依角色提供，不預設每份報表都包含完整敏感欄位。

## 12. 驗收情境與估算前提

以下為 Scope 核定後應落地的驗收基準，本次尚未開發或執行功能測試。

| ID | 情境／通過條件 |
|---|---|
| AC-01 | 業務能以模板複製下一檔活動並修改規則、內容與期間；不用每次改程式。已送出 Claim 保持原版本可追溯。 |
| AC-02 | 驗證信箱但未證明 AORUS 資格，不可被視為會員已通過；未授權者不能讀取或補件別人的 Claim。 |
| AC-03 | 同張發票可加多品類產品，超出每品類／每人／每戶限制會攔阻或進有紀錄的人工判斷；不以拆單避限。 |
| AC-04 | 不同居住／購買／銀行國的合法跨境案例可選到合格通路；自由輸入但不在名單的通路不直接通過。 |
| AC-05 | 購買滿 14 天、起迄邊界、購買已截止但仍能申請、活動停收但仍能補件等情境符合核定規則。 |
| AC-06 | 在核定的活動／互斥活動去重範圍內，同 SN 同時送出只能有效占用一次；更換 SN 及重新申請仍保留可查核關聯。 |
| AC-07 | 補件保留舊資料；會員／SN／RMA 結果顯示於案件；異常即使已核准仍阻擋新付款，解除有理由。 |
| AC-08 | Q4 若在 Scope：缺 A、A 不合格、重複品類、非同發票、移除品項都會重新判斷 B 區加碼。 |
| AC-09 | 多件並發申請不超支；R→A→P 不重複扣款；補件、拒絕、調額、付款失敗／Unknown 不產生錯誤釋放。 |
| AC-10 | 未核放或 Hold 的案件不能付款；同邏輯指令重試／重複匯出不能造成第二次付款；未知結果先查核。 |
| AC-11 | 部分成功的批次能逐筆對帳；寄信成功不誤報現金已付；失敗、更正及重送均有可追溯結果。 |
| AC-12 | 收件、補件、核准／拒絕及付款通知與案件一致；客戶可受控地補件、更正或提出取消，客服能看到歷程。 |
| AC-13 | 案件／產品件數、幣別、預算與付款報表可與明細核對；敏感下載及不同角色資料範圍測試通過。 |
| AC-14 | 首波各語言／幣別、必要 RTL、附件格式、行動版及截止時區經核對，沒有沿用錯誤季別條款。 |
| AC-15 | 若宣告可營運，完成一個受控端到端付款與對帳驗證，且五項上線門檻均有責任人確認；否則只驗收為 UAT。 |

正式估算前需至少取得首波活動矩陣、上線模式、帳戶／會員方式、付款方式、營運量、附件量及 API 時程。現有截圖不能代替報表欄位表、付款格式與例外 SOP；本稿不據此虛構工期或費用。
